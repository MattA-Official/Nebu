# 0040. DMB

- **Status:** Proposed
- **Date:** 2026-11-05

## Context

NeOS's kernel tells a server when the last capability with a badge goes, by writing
the badge into a ring in a frame the server shares
([NeOS ADR 0078](https://github.com/MattA-Official/NeOS/blob/main/docs/decisions/0078-notices-when-the-last-capability-goes.md)).
The kernel and the server may run on different cores, so each orders its accesses to
the ring with a fence: Rust's `fence(Ordering::SeqCst)` and `fence(Ordering::Release)`,
which compile to `dmb ish`. Nebu halts on DMB, since it implements ISB and DSB but
not this one.

## Options

- **Use load-acquire and store-release instead of fences**, which Nebu runs (ADR
  0030). In NeOS that needs new `unsafe` code in both the kernel's and the runtime's
  audited cores, to make atomics out of shared memory, where a fence needs none.
- **Implement DMB** _(chosen)_, decoded with the other barriers. Nebu runs its cores
  in turn, one instruction each, and models no caches or write buffers, so every
  access is already seen in program order: like ISB and DSB, DMB has nothing to do.

## Decision

1. DMB is decoded with every option, as DSB is, and does nothing.

## Consequences

- Nebu runs NeOS's `notices` scenario, and any later code that uses fences.
- If Nebu ever models out-of-order memory, DMB must then order it.
